
#### OOP Concepts — SDET Interview Answers (7+ Years, Payment Domain)

| OOP Concept       | Simple Definition                                                                | UI Automation Answer                                                                                                                                                                                                                                                                                                                                                                                                                               | API Automation Answer                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Encapsulation** | Keep your internal things private. Only give others what they need to use.       | In my Page Object Model, I keep all locators as **private** variables. Test classes cannot touch them directly. They can only call public methods like `login()` or `clickSubmit()`. So if a locator changes tomorrow, I fix it in **one place only** — not in 50 test files.                                                                                                                                                                      | In my payment framework, I keep sensitive things like **auth tokens, headers, and card details** inside a `PaymentService` class as private. Nobody outside can read the token directly. They can only call public methods like `initiateRefund()` or `createPaymentOrder()`. Token refresh and header building happen silently inside.                                                        |
| **Inheritance**   | Child class gets everything from parent class. No need to write same code again. | I have a `BaseTest` class. It has driver setup in `@BeforeClass`, driver quit in `@AfterClass`, and screenshot-on-failure logic. All my test classes do `LoginTest extends BaseTest`. They automatically get all of this — I never write driver setup again. Same for `BasePage` — all page classes extend it and get the driver reference for free.                                                                                               | I have a `BaseAPI` class. It sets the base URI, default headers, and creates the auth bearer token. Then `PaymentAPI extends BaseAPI` and `RefundAPI extends BaseAPI`. Both classes get authentication for free — they only define their own endpoint methods on top.                                                                                                                          |
| **Polymorphism**  | Same method name, different behavior depending on which object calls it.         | I have an abstract method `isPageLoaded()` in my `BasePage` class. Every page overrides it differently — `LoginPage` checks if the login button is visible, `CheckoutPage` checks if the cart is loaded, `PaymentPage` checks if the payment form appeared. My utility calls `page.isPageLoaded()` without knowing which page it is. The correct check runs automatically. That is **runtime polymorphism**.                                       | I have a `ResponseValidator` interface with one method `validate(Response r)`. Then I create `PaymentValidator`, `RefundValidator`, and `WebhookValidator` — each one validates differently. My test runner calls `assertResponse(validator)` without knowing which type it received. The right validation runs automatically. Adding a new validator needs **zero changes** to existing code. |
| **Abstraction**   | You define WHAT something must do. You hide HOW it does it.                      | I create an abstract `BasePage` class with abstract methods like `isPageLoaded()` and `getPageTitle()`. Every page class **must** implement these — that is the contract. A tester using `LoginPage` knows it has `isPageLoaded()` but does not care whether it checks a URL, a spinner, or a specific element. The *what* is visible. The *how* is hidden. *(Note: Encapsulation hides data. Abstraction hides implementation using a contract.)* | I create an `IPaymentGateway` interface with methods like `processPayment()` and `verifyStatus()`. Then `RazorpayGateway`, `StripeGateway`, and `PayUGateway` each implement it in their own way. My tests only talk to the interface — not to any specific gateway. If the client switches from Razorpay to Stripe tomorrow, **not a single test file changes**.                              |

---

#### Quick Difference: Abstraction vs Encapsulation

|                          | Encapsulation                            | Abstraction                                                       |
| ------------------------ | ---------------------------------------- | ----------------------------------------------------------------- |
| **What it does**         | Hides data using private/public          | Hides implementation using interface/abstract class               |
| **Example**              | Private locator, public `login()` method | `IPaymentGateway` interface — tests don't know which gateway runs |
| **Question to remember** | *"Who can access this?"*                 | *"What must this do — and who cares how?"*                        |

#### One-line Memory Tricks

- **Encapsulation** → *"My locators are private. Call my method, don't touch my field."*
- **Inheritance** → *"BaseTest does the boring setup. My tests just extend and focus on testing."*
- **Polymorphism** → *"Same method call. Different page. Correct behavior. Automatically."*
- **Abstraction** → *"I define the contract. Each class fills it differently. Tests don't care."*
